# pi-agency

## Purpose
all things related to agents, subagents, etc

## Dependencies
- tandem
- worktrunk

## Domains

[pi-herdr](../pi-herdr/README.md) owns every native HC registration (inbox, read-only helper profiles, Task-backed and Task-free Workers, idle compaction) and reuses the modules below; `pi-agency`'s own entry registers northstar (`notes`, `history` and `nstar` hooks), and the orchestrator model policy. The retired legacy Herdr implementation (pane-backed `subagent_*`/`worker_*`, Herdra widget, Ceph naming/lead hooks, SSH pane routing) remains in Git history only (task-551).

- `subagents/profile.ts` loads the bundled `agents/*.md` helper profiles (`scout`, `researcher`, `reviewer`) that `pi --agency-profile <name>` applies through pi-herdr.
- `workers/` holds the native Worker brief, managed context, report schema and control records, and the shared Task/Worktrunk/Git authority that pi-herdr's Worker tools use. Workers are the only delegated mode that may mutate project files. Their owner retains Tandem transitions except the scoped `worker_progress` milestone actions, plus integration, acceptance, and cleanup authority.

`pi-agency` owns the agent inbox contracts, receiver, journal and UI; pi-herdr registers them. `agent_send` takes one explicit `terminal`: a local HC name/address, or `machine/terminal` on a machine from `hc machine ls`, resolved by its own core per send. There is no saved Herdra-id registry, composer transport or duplicated inbox. Cross-machine delivery uses native `hc exec --on` into the receiver's own `inbox drop` (see pi-herdr README).

Inbox implementation:

- `inbox/` owns `agent_send` (its logic is `sendAgentMessage` in `inbox/send.ts`, which other extensions such as `/task` call too): a message is an envelope (`envelope.ts`: id, kind `request`/`result`/`blocked`, `reply_to`, from/to addresses with machine/label and native HC terminal/permanent-core id, body) written by temp file + rename to `~/.local/state/pi-agency/inbox/hc:<permanent-core-id>:<terminal>/`. The Pi session at that terminal watches its folder, delivers each file with `pi.sendMessage` as a `pi-agent-message` carrying the full envelope (idle: followUp + triggerTurn; busy: steer), never through the composer, then deletes it. Leftovers are delivered on `session_start`; `agent_settled` rescans. Each machine appends one JSON event per line to `~/.local/state/pi-agency/inbox/log.jsonl` (local, untracked, rebuildable from transcripts): a body is stored once per machine, in the `send` of a message this machine sent or in the `deliver` of one it received from another machine (that is this machine's only copy of its text), and `deliver`, `fail`, `close` and `reopen` are otherwise references (`deliver` is `{op, id, at, session}`; the others carry id, at and a note). No headline field is stored: it is body line 1, derived on every read. `open.json` beside the journal is the open index the same append path rewrites atomically after each append (`{v: 1, stamp, open}`, stamp = journal size and mtime); `inbox open`, the `/inbox` overlay, northstar's open items and the turn label read it, and a stale stamp, a missing file or unreadable JSON rebuilds it from the journal, so it is an optimisation and never the truth. A writer killed between the append and the index rewrite therefore leaves only a stale index; a writer killed mid-append leaves a partial last line, which readers skip and the next writer cuts off before appending. The journal was cut over on 2026-11-11 with no migration: the previous journal is archived compressed under `~/Backups`, messages open at that moment were closed with a cut-over note, and the journal and index started empty, so `inbox thread`/`reopen` for a pre-cutover id no longer work. Line 1 of the body is the headline and the answer: `agent_send` (and the pi-herdr `report` tool) rejects a first line over 160 characters with `put a one-line headline first, details below` and sends nothing (task-557). An address's `label` is the sender's or recipient's HC name, or the Herdr app's `<space> / <tab>` (its native `where` label) for an unnamed terminal, or `unnamed`; the inbox header, `inbox` CLI rows and `/inbox` always show the actual address beside it in parentheses (task-558). A request or blocked message is open until it closes itself or is closed by hand (task-556): a reply (`reply_to`), a dispatch naming it (`dendra_start`/`manus_start`/`ceph_start` `from:`, note `dispatched to <name>`), or its linked Task completed or cancelled through Pi (`tandem_close`, `worker_finish`; note `<project> <task-N> completed|cancelled`). Its linked Task is the sender's hc `task=` label (`<project>:<task-N>`, set on every manus), else the first Task id its text names (`task-N` matches that id on any board, `project:task-N` only on that project's). Closes are recorded in this machine's log only; Task completions outside Pi (the Tandem CLI or TUI) close nothing. In log order the last reply, close or reopen wins, so `inbox reopen <id>` undoes any close and `inbox open`/`thread` show it. `agent/scripts/inbox` prints open, recent and thread views and closes and reopens messages; `inbox thread` also shows each message's delivery (`queued`, `delivered`, `failed`, or `queued on <machine>` for another core) and its recipient's current hc status (idle, working, done, blocked, error), read once from that core (task-555); a message received from another machine is in this machine's journal while it is open, and once it closes its text lives only in the receiving session transcript named by its delivery. `agent_send` reports the recipient's status when it queues a message and what it means for delivery (idle: a turn starts now; working: steered into the current turn; blocked: waits). `/inbox` opens the same views as an overlay for Algorant. An address's `machine` is this machine's name: the machine-local global `settings.json` entry `"pi-agency": { "machine": "<name>" }` when set (for a machine without Tailscale), otherwise the Tailscale short name; with neither, inbox calls fail clearly (no hostname guessing).

Idle compaction lives in `pi-herdr/compaction.ts` (see the [pi-herdr README](../pi-herdr/README.md)); it reuses the inbox gate from this extension.

`state.ts` holds the shared local-state primitives, with no Pi imports so the `inbox` and `whois` CLIs load it: `stateDir()` (`$XDG_STATE_HOME`, else `~/.local/state`), `writeAtomic()` (dot-temp beside the file, then rename), `tandemShow()` and `newId()`.

## Northstar

`nstar.ts` binds one job: native Worker control records and manus labels bind automatically; Herdra/Ceph use `notes {taskId}` or `notes {label, brief}` explicitly. Unbound means no note and no capture. A Task is only read (`tandem show`): its title, relatedFiles and constraints frame the note, and nstar never writes the Task body. A Task-backed job's captures (inputs, hand-offs, next, notes) are custom entries in its Pi session; Task-free work keeps the whole note in `.pi/notes/<work-label>.md` in its checkout, written atomically and ignored locally through Git `info/exclude`. No global note, registry, evergreen file, or Task-backed file fallback.

`nstar-note.ts` maintains the leading goal/limits/Algorant-inputs/next-step block and free working notes. A one-use editor snapshot on the SDK submit binding allows exact-matching bound pane input as verbatim **Algorant (direct)**; CLI, RPC, HC bootstrap and unmatched input are not direct capture. Custom editors/submission keys bypassing the SDK binding are not captured (there is no source-enum fallback); starter inbox bodies are **relayed by <whois label>** verbatim with their message id; other inbox messages and outgoing reports are agent hand-offs of one line (headline or report summary) plus a link to the record (`inbox thread <id>`, `worker_handoff <name>`). No text is classified as approval. The newest twenty full input/hand-off entries stay in the block; older material remains only in existing history. There is no automatic next-step placeholder. `notes` can set next or append agent notes (goal/limits only for Task-free notes), never the protected input/hand-off sections or a native binding. Recorded context grants no new authority.

Task bodies written before task-597 may still lead with a northstar block; Worker briefs and scope comparison skip that region. Archived Tasks are read-only, including hooks. No shadow note is created.

nstar is the only post-compaction injector. On `session_compact` (manual, automatic, idle, or a provider's remote compaction) it records ONE injection for the new window: the job's block plus this terminal's open inbox requests and blockers, read in process from the inbox log; the non-persistent `context` hook prepends it (and publishes it as a context prefix for remote replay). It does not own compaction. One best-effort reminder per context window starts at 55%, before idle compaction at 60%, asks for the next step, and starts no new turn. `history` is the sole bounded read-only known-phrase recovery path: at most five matching files of at most 10 MiB, five user-role excerpts of 1200 characters each; only an explicitly requested other-machine conversation permits the homelab-server synced store. It creates no session cache/database and never rewrites history. Both tools use existing pi-ui compact/expanded/error cards.

## Worker context

`workers/brief.ts` is the one formatter for the captured assignment, operating instructions and report template. Version-6 delivery records add an explicit `planRequired` policy alongside the existing assignment and plan approval. Plan approval is explicit: `worker_feedback` approves a pending plan only with `approve: true`; without it the call is a revision request, and `approve: true` on anything but a pending plan fails before sending. A Worker may submit a new plan at any time; it clears the earlier approval. A rejected `worker_report` is not delivered; the Worker is told so and can fix and resubmit in the same turn, or `worker_ask`. Only when its turn then ends (an assistant message stopped normally with no pending tool call) with the latest `worker_report` result of that turn still an error does the `agent_settled` path mark the delivery failed with the error and attempted summary, which the owner receives through the existing `pi-worker-handoff-failure` notice (one per distinct diagnostic; `worker_feedback` then opens a new delivery, as for provider errors). Limit: no notice while the Worker can still retry, when the delivery already has a report or question (the owner already has it), or when the rejection precedes an owner steer message in the same turn. Revised ready reports must summarize the complete verified outcome, files and evidence. Parent prompts contain only `Parent request:` and the direction; full-brief replay has been removed. Native Task claim completes before the first prompt.

`workers/context.ts` enables managed context with `--worker-context` and stores only a session-bound mode entry in Pi history. A separate peer's new session ID cannot inherit Worker mode. Existing native Workers can adopt on `/reload`. A session-file-bound `worker_context` capability is advertised once per runtime lifecycle; parent dispatch checks it using its existing agent read and refuses old receivers with a reload instruction. This is not a readiness poll or an acknowledgement on each message.

| Boundary | Behavior |
| --- | --- |
| Agent run starts, including background/custom-message wakeup | Resolve current native Worker/delivery/session/source identity and load the existing delivery record once. Missing or invalid context explicitly aborts; an in-memory tool guard stays closed. Exact-record failures use existing handoff-failure publication; unresolved identities remain visible diagnostics, never guessed records. |
| Subsequent model/tool rounds | Prepend the already-rendered brief through Pi's non-persistent `context` hook. No extra process or filesystem lookup per round. |
| Compaction | The brief is outside the summarized history and is supplied again on the next request. Summaries describe conversation/work, not the authoritative assignment. |
| Recovery | Reattach without rescoping a running Worker. The captured brief and approval remain unchanged. All resumed work uses the same fresh-assignment continuation path; resume cannot approve a pending plan. |
| Settled approval (`approve: true`), plan revision, answer, correction or resume | Capture current Task scope into a new delivery. Send only the short direction; the next run reloads the brief. In-flight steering retains the current assignment. |
| Reload or session replacement | Restore mode for its exact session and reconstruct the brief from native binding on the next run. A native Worker fork/new session cannot take over the old delivery: restore the captured session or resolve the attempt explicitly. Independent peers do not inherit Worker mode. |

`lib/context-prefix.ts` is a small same-process event contract, not a Task store. OpenAI remote replay preserves the same transient prefix after its immutable replacement history and before the live tail. It never saves that prefix into its opaque/replay state. Ordinary provider paths use Pi's context transform directly.

Reload affected orchestrators and Workers after updating shared resources. If an old delivery lacks the new policy, refresh it through owner recovery/continuation; do not guess that an absent policy makes planning optional. Old transcripts and report evidence are not rewritten, so pre-cutover full briefs can still exist as historical messages. There is one current runtime brief and no new full chat copies. Smaller history does not by itself establish provider-cache, billing or latency savings.

## Bundled resources and defaults

`agent/model-roles.json` is the only source of default models (task-404); `model-roles.ts` is its single loader. It holds an ordered list per role (`orchestrator`, `worker`, `subagent`, each entry `{model, thinking, fast?}`) plus a `review` block (`enabled`, `models`) read by the adversarial review rule (task-407): a `reviewer` launch (`resolveReviewEntry`, which applies `checkEntry` and so the quota gate) takes the first available `review.models` entry whose company differs from the caller's current model (`provider/id` of `ctx.model`; a Worker's own model for a Worker caller). `PROVIDER_COMPANY` in `model-roles.ts` maps provider to company explicitly (`anthropic` → anthropic; `openai`, `openai-codex` → openai; `xai` → xai); aggregators `github-copilot` and `opencode-go` map by model family instead (`MODEL_FAMILY_COMPANY`: `claude-*` → anthropic, `gpt-*` → openai, `deepseek-*` → deepseek). An unmapped provider or family is an error, not a guess. It fails before creating anything when review is disabled, either company is unmapped, or no opposite-company entry is available (each rejection listed). The file also requires `quota.weeklyThreshold` and `quota.fiveHourThreshold` (numbers above 0 and at most 1, both currently `0.9`; no defaults, missing or invalid values fail the load). The first available entry wins, where available means the model is in the catalog, its provider has credentials, its provider is allowed on this machine (when the machine-local global `settings.json` sets `"pi-agency": { "modelProviders": [...] }`, only those providers count, read by `local-settings.ts`), and (task-406) for `anthropic` and `openai-codex` its weekly usage is below `quota.weeklyThreshold` and its 5h usage is below `quota.fiveHourThreshold` (`checkEntry`, the one per-entry check, called by `resolveRoleEntry`). The quota gate is launch-time only and synchronous: it reads the cached provider-wide `Week` and `5h` windows that the powerbar keeps in `~/.pi/cache/powerbar-{anthropic,codex}-usage.json` (per-model windows such as Opus, Sonnet and Spark are not gated). Missing or malformed cache, no `Week` window, no matching window, or a window whose `resetAt` has passed counts as unknown and does not gate, so a failed quota fetch never blocks launches; a stale reading at or above the threshold still gates until its reset, since weekly usage only rises within a window. Known gap: the powerbar refreshes only the active model's provider, so a stale low reading for another provider can still select it while it is actually over; there is no live fetch at launch. Orchestrator sessions are not switched mid-session. With no available entry the launch fails before creating anything, with an error naming the role and why each entry was rejected (including quota, with the percentage and time to reset). The orchestrator and helper-profile launch notices also list skipped entries and their reasons. A native helper (`--agency-profile`) resolves the `subagent` role (a reviewer the `review` block) and a Worker the `worker` role; explicit Worker `model` / `thinkingLevel` win (an explicit model skips the list and takes the role's first entry's thinking; an explicit thinking level replaces only the chosen entry's), then the file. The file is read on every launch, so edits apply to the next one. `fast: true` is declarative: the entry must be eligible for the existing Fast policy or the launch fails; the priority tier itself is requested by the `pi-providers` OpenAI Fast policy (on by default) in the child session. Interactive main sessions (Herdra, Cephs, manus) apply the `orchestrator` entry at fresh `startup`/`new` through `model-roles-session.ts`: it sets the session model and thinking level (including the configured thinking level) and notifies. It is skipped for Workers, resumed sessions, reload/fork, non-TUI runs, and when the command line carries `--model`, `--models`, `--provider` or `--thinking`; with no available entry it only notifies an error and leaves Pi's startup model alone. It does not write Pi's saved defaults. `--model provider/model:thinking` and `--models provider/model` select the child independently of parent/Worker defaults. The skill owns the selection workflow.

Algorant explicitly approved direct `xai/grok-4.7` as a numbered-model exception (2026-11-13, task-713): 4.7 is the verified selectable version and `xhigh` its supported maximum, not a `max` model suffix. Keep it last in `review.models`: Fable or Astra is considered first according to the author's company; Grok is the fallback when earlier entries are unavailable, not the default. The workstation's approved provider filter is `["anthropic", "openai-codex", "opencode-go", "xai"]`; existing sessions retain their current model.

**Named model sets (task-714).** The optional root `sets` in `model-roles.json` holds named sets (`^[a-z][a-z0-9-]*$`), each filling some of `herdra`, `orchestrator`, `worker`, `subagent` (one `{model, thinking, fast?}` each) and `review` (an ordered non-empty list); a role a set leaves out is no target for it, never a fallback. A machine opts in with the machine-local `"pi-agency": { "modelSets": { "herdra": <set>, "orchestrator": <set>, "worker": <set>, "subagent": <set>, "review": <set> } }`: all five roles, never together with `modelProviders` (both is an error; `local-settings.ts` checks only this shape). Opted in, each role resolves only from its selected set, which must exist and fill that role (all five are checked at resolution): no cross-set or legacy fallback and no provider filter; an unavailable target fails naming the set, role and reason (`Model set "<set>" <role> target <model> is unavailable: <reason>. No fallback to other sets.`). For a configured `claude` or `openai` review set, a Reviewer first routes by the author's company: an Anthropic author uses `claude.review` (Astra, then Grok), an OpenAI author uses `openai.review` (Fable 5.2, then Grok); other author companies retain the configured row. Explicit `grok` and custom review sets stay exact. The original complete map is validated before routing, and a missing routed row fails clearly. Only that effective row is checked for opposite-company/catalog/auth/quota eligibility, with no fallback to another set after rejection; returned `set` and notices name the effective row. Set quota, for `anthropic`, `openai-codex`, `xai` and `opencode-go` from the same caches, counts only current (reset still ahead) provider-wide `5h`, `Day`, `Week` and `Month` windows at a fixed 90%: a window at or above it blocks until its reset at any reading age; a reading at most 30 minutes old with all windows below it is `checked`; no reading, an older low reading or no current window is `unknown` and proceeds. `ResolvedRoleEntry.set` and `.quota` (`checked: …`/`unknown: …`) carry this; `skipped` lists only rejected entries. The selected set and quota line appear once per launch: the orchestrator notice, the helper/Reviewer profile notice, and a notice once a native Worker launch is confirmed (also in its start result text). A fresh main session whose native HC name is `herdra` takes the `herdra` row, every other one the orchestrator row; if that fails it notifies and refuses every turn until a model is chosen explicitly (`/model` or a cutover request), so it never runs on its unchecked startup model. A `"pi-agency"` section that contains `modelSets` but fails validation (`LocalAgencySettingsError.modelSets`) refuses the same way instead of reading as legacy. Without `modelSets` everything above this paragraph applies unchanged, and the benchmark selector never reads sets. Loading fails for any `opencode-go` entry of the `claude`, `gpt` or `grok` family (no approved exception). The matrix's numbered model ids are Algorant's approved 2026-11-13 exception. Rollout precondition: a host must run and have reloaded this loader before it pulls `sets` data or writes `modelSets`, because older loaders reject both unknown keys (and the older settings reader also breaks inbox addressing); a pull does not guarantee every running Pi reloads.

Go is for models the major providers do not sell directly (currently mostly DeepSeek). Never route Anthropic, OpenAI or xAI models through Go unless Algorant explicitly requests that route; the Go Luna and Grok review entries are removed. Algorant's exact direction, recorded with this version exception:

> "Grok will never be accessed through opencode. ever. unless I'm for some strange reason specifically asking for opencode to use a major providers models, it shouldn't happen. I use opencode go to access newe models and mostly just deepseek for cheapseek currently as of nov 2026. this can change."

The native Worker dispatch tool does not expose a general model or thinking override. Its optional `benchmarkModel` is a closed selector for the approved Luna/Sonnet pair at fixed high thinking. `resolveBenchmarkWorkerModel()` reuses the per-entry catalog/auth/quota checker; its provider exception is internal to this named path and applies only to the selected exact contender. Benchmark checks run before each new Worker invocation, including feedback, answer and resume continuations; recovery-only adoption does not launch a model. Each check requires a cache fetched within 30 minutes, a current Week below 90%, and every reported Week/5h window below 90%; Week is mandatory, absent 5h is surfaced as `not reported`, and stale/malformed values fail closed. This does not alter ordinary `resolveRoleEntry` behavior, model-roles data, helper/reviewer selection, or defaults. Luna's Fast mode is on from pi-providers' existing per-session default.

Reload/restart after installation before safe live verification: a long-lived Pi picks a merged `~/.pi` change up at its next turn start (`pi-herdr`'s self-reload, `reloaded to <fp8>`), and `/reload` is the forced path for a Pi still running older code. For tracked changes under `~/.pi`, merge first, then validate live.

## Tandem board sync and merge safety

Tandem syncs its board through the `tandem` branch itself; source Git operations are independent. Mutations report `data.sync`. `pending` means saved locally, not failed. Temporary IDs remain valid after numbering. Linked Worktrees have no `.tandem/`; commands run from a Worker checkout use the main worktree's board. Surface conflicts and held edits to Algorant and resolve them only through `tandem sync resolve` when authorized.

Never stage, commit, push, edit, delete, or rename `.tandem/` or the `tandem` branch. Do not require pending board state to be clean before Worker start, integration, or source push. `worker_finish` requires a clean Worker source but performs no target-clean preflight: non-overlapping staged, unstaged, and untracked target changes are preserved by Worktrunk, which remains the sole authority refusing overlapping paths, conflicts, in-progress Git operations, and hook/synchronization failures.
